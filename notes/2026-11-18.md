Three under-the-hood PRs: tournament creation now saves in one transaction (and only into your own clubs), the startup CDN experiment is over, and usage metrics land in the right session. The tournament migration isn't on live yet, so production deploys are blocked.

## Shipped

**Fixes**

- Creating a tournament saves the tournament and its rules in one transaction, so a failed rules write can no longer leave a half-made tournament behind. Only members of a club can create a tournament in it (before, any signed-in user could). The 879-line wizard is split into a draft core, two hooks and one component per step. Screens are unchanged (#329, closes #325)

  No screenshots: all 15 affected screens, `tournament-create` included, are pixel-identical before and after.

  ```mermaid
  sequenceDiagram
    participant App as App (tournament wizard)
    participant PG as Postgres / RLS
    App->>PG: rpc save_tournament(p_tournament, p_rules)
    PG->>PG: auth.uid() set? (else 42501)
    PG->>PG: validate title, club, start date, roster, price, status (22023)
    PG->>PG: caller is a club_members row for that club? (else 42501)
    PG->>PG: insert tournaments (insert policy: creator + club member)
    PG->>PG: insert tournament_rules (defaults filled)
    PG-->>App: new tournament id (or nothing saved)
  ```

  **Model changes**

  | Object | Change | Notes |
  | --- | --- | --- |
  | `save_tournament(p_tournament jsonb, p_rules jsonb) → uuid` | added | SECURITY INVOKER, `authenticated` only (revoked from anon). Writes tournament + rules or neither |
  | Policy "creator can insert tournaments" on `tournaments` | changed | Now also requires the creator to be a member of the club |

- Usage metrics: events tracked before the first session opened (the first screen, banners, the first feed paint) now carry that session's id, a new session records the current screen again, and `feed_first_paint` reports `landing`, `wait_ms` and an honest `ms` from when the launch was on screen (#328, closes #326)

**Under the hood**

- Ended the startup CDN experiment: the update check and feed ads are read straight from Supabase on every open, and `/api/startup` is removed. Direct reads had p50 365 ms vs ~1.6 s for the CDN arm (#327, closes #324)

No diagrams for #327 / #328 (client-side only, no schema change).
